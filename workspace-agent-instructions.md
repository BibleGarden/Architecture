# Bible Garden: рабочие инструкции агента

Канонический источник для корневого `cep/AGENTS.md`. Сам этот файл — документация
workspace, а не инструкции, ограниченные репозиторием `Architecture`.

## Карта проекта

Рабочий каталог содержит независимые git-репозитории; локальное имя совпадает с
именем репозитория. Схема сервисов: `Architecture/architecture.md`
([GitHub](https://github.com/BibleGarden/Architecture/blob/main/architecture.md)).

| Папка | Назначение |
| --- | --- |
| `Bible-API/` | Публичный FastAPI API и импорт опубликованных данных |
| `Dashboard-API/`, `Dashboard-Web/` | Административный API и интерфейс |
| `bible-parser/` | Подготовка текстов и аудиовыравниваний |
| `AI-Evaluation/` | Оценка моделей и результаты |
| `Architecture/`, `Deploy/` | Архитектурные решения и приватная эксплуатация |
| `Site/` | Статический сайт |

Локальный запуск: `Deploy/local-development.md`
([GitHub](https://github.com/BibleGarden/Deploy/blob/main/local-development.md)).
Продакшен менять только по `Deploy/runbook.md`
([GitHub](https://github.com/BibleGarden/Deploy/blob/main/runbook.md)), никогда не
через `scp`.

## Правила работы

- Общаться с пользователем по-русски; код и комментарии — по-английски. Не хранить
  секреты в git; `.env` существует вне репозиториев.
- Незаданная или некорректная критичная конфигурация должна явно останавливать
  запуск с названием переменной. Не маскировать её fallback; осмысленные дефолты
  допустимы только для операционных параметров.
- Документацию об изменённом поведении обновлять в той же ветке и MR. Архитектурные
  решения — в `Architecture/decisions/`, эксплуатационные сведения — в `Deploy/`.
- Перед работой получить свежий `origin/main`; работать в ветке от `main`, не
  коммитить в `main` и не переписывать существующие коммиты без запроса.
  Проверенную работу коммитить и пушить самостоятельно.
- Выполнять быстрые проверки по масштабу правки, долгие оставлять CI. Не retry CI
  без явного разрешения пользователя и не создавать второй MR-pipeline после push.

## Данные и продакшен

- Единственный источник контента — локальная `cep_admin`; поток только
  `cep_admin` → `cep_public`. Детали: `Deploy/data-flow.md`
  ([GitHub](https://github.com/BibleGarden/Deploy/blob/main/data-flow.md)).
- Тексты, выравнивания, ручные fixes и аномалии править в локальной админке.
  Экспорт применяет manual fixes через `COALESCE`.
- Прод меняется только штатным импортом API. Перед изменением создать бэкап
  затронутых таблиц в `/root/db-archives/` с номером задачи; успех — только
  `status == "ok"`, не HTTP 200.
- Если импорт планирует удалить перевод, сначала проверить причину в `cep_admin` и
  создать бэкап; лишь затем явно передать `allow_removals=1`.
- Прямой SQL на проде возможен только с решением владельца данных и обязан сохранять
  `COALESCE`-семантику ручных правок. Продовая статистика не импортируется и не
  затирается; продовая админка предназначена только для просмотра.
- При изменении текстов RAG-порядок: локальный импорт → `chunk_cli` → `index_cli`
  → продовый импорт. Полная процедура находится в `Deploy/runbook.md`.

## Задачи и делегирование

- В ClickUp взятую задачу сразу ставить «в процессе», завершённую — «контроль» или
  complete. Для «контроля» написать, что проверяет человек; complete — только после
  этой проверки. Инцидентную работу оформлять задачей.
- Оркестратор сам ведёт техническую работу через постановку, исполнение, независимое
  ревью, проверку, тикет и MR. Спрашивать пользователя о продукте/UX, деньгах,
  релизе, изменении принятых правил и моделей и нестандартных действиях на проде.
- Приоритеты: безопасность данных, качество, документация. Механику, документацию и
  ClickUp поручать Sonnet; разработку, диагностику и ревью — Opus; Fable — только
  если Opus недостаточно. В AI-работе оркестратор лично не тестирует гипотезы:
  исполнитель сверяет постановку с живой системой, результат проходит независимое
  ревью.

## AI и оценка

- Продукт должен быть доступен без возрастных и страновых ограничений. Цель —
  собственно развёрнутые модели или модели без таких внешних условий; Anthropic или
  OpenAI API не является заменой.
- Принятые модели: Gemma 4 31B IT для вопросов, Qwen3-30B для rewrite и rerank,
  bge-m3 для embeddings. Основания и граница с runtime: `Architecture/decisions/0002-ai-model-provider-policy.md`
  ([GitHub](https://github.com/BibleGarden/Architecture/blob/main/decisions/0002-ai-model-provider-policy.md)).
  Реальный runtime проверять по `Deploy/`.
- Сохранять pipeline: rewrite → embeddings и BM25 → interleave → blacklist →
  diversity → rerank. Не возвращать семантический индекс вместо rewrite без новых
  измерений. Не менять `AI-Evaluation/evaluation/thresholds.json` и `scenarios.json`;
  неразмеченные top-1 отдавать пользователю, не размечать самостоятельно. При vLLM
  temperature 0 сравнивать тёплые прогоны.
- Перед публикацией соблюдать требования площадок: Google Play требует жалобу на
  ответ генеративного ИИ, Apple — согласие на передачу данных стороннему ИИ; для
  материкового Китая отдельно проверить местные разрешения.

## Документация и синхронизация

- Специфика сервисов: `Bible-API/CLAUDE.md`, `Dashboard-API/CLAUDE.md` и
  `AI-Evaluation/README.md`. Текущая эксплуатация: `Deploy/runbook.md`,
  `data-flow.md`, `prod-topology.md`, `env-checklist.md`, `operations.md`.
- После merge этого файла синхронизировать корневой `AGENTS.md` точной копией:
  `cp Architecture/workspace-agent-instructions.md AGENTS.md`. После свежего clone
  сначала получить `Architecture`, затем выполнить ту же команду. Источник истины
  остаётся в `Architecture/`.
