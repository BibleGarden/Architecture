# ADR-0012: Static site generator with committed HTML for bible.garden and lampada.app

- Status: Accepted
- Date: 2026-09-21
- Approval: Maria's decision on the publishing infrastructure, 2026-09-21 (ClickUp 86cbj99hv)

## Context

Both public sites live in `BibleGarden/Site` as hand-written HTML. Language was
switched by JavaScript (`data-i18n`, `?lang=`), so search engines indexed only
the English text, and `robots.txt`, `sitemap.xml` and unknown URLs returned the
landing page with status 200. The SEO content plan
(`Site/docs/seo/semantic-core-and-content-plan.md`, section 3.2) requires
indexable language pages with `canonical` and `hreflang`, a sitemap, structured
data and `llms.txt` before the first articles are published. Production nginx
serves the `main` checkout of `Site` read-only (`Deploy/prod-topology.md`); there
is no build step on the server and no deploy pipeline.

## Decision

Articles and landing pages are generated by a small Python script in the `Site`
repository (`sitegen/`: Python-Markdown + Jinja2 + PyYAML, pinned in
`requirements.txt`, no Node toolchain, no framework, no plugins). Sources are
Markdown with YAML frontmatter under `content/<site>/articles/<slug>/<lang>.md`
and YAML translation files under `content/<site>/i18n/`; templates live in
`templates/<site>/`.

The generated HTML is committed to the repository next to its sources. The
production server keeps serving a plain checkout of `main`; nothing is built or
installed there, and the nginx configuration does not change. GitHub Actions
rebuilds the site on every pull request and fails when the committed output
differs from the build or when a JSON-LD block does not parse. The build is
deterministic (no timestamps), so a clean tree proves the output is current.

URL structure: `/`, `/ru/`, `/uk/` for landing pages and `/articles/<slug>/`,
`/ru/articles/<slug>/`, `/uk/articles/<slug>/` for articles, one slug per topic
in every language; `hreflang` links only the published versions. Hand-written
pages with permanent App Store URLs (`privacy.html`, `lampada/privacy/`,
`lampada/support/`) stay outside the generator.

`/` is the English page and `x-default`, not a redirector to `/en/`: the App
Store listing and already indexed results link to `/`, and crawlers without
JavaScript must find content there. Language selection stays client-side: a
legacy `?lang=` link redirects to the language URL; on `/` a language chosen
explicitly through the switcher (kept in `localStorage`, including English)
wins, otherwise a browser that prefers `ru` or `uk` is sent to `/ru/` or
`/uk/`. Crawlers and English-first browsers are never redirected, and the
language versions of every page remain plain links (Maria, 2026-09-21).

## Alternatives considered

- Hugo, Eleventy, Astro or another static site generator: more capable, but
  adds a toolchain (Go or Node) and a theme layer for two landing pages and a
  handful of templates; the landing pages would have to be ported into a
  foreign template system.
- Building on the server or in CI with deployment: changes the production
  topology (`Deploy/`), needs credentials in CI and a deploy procedure for a
  site that today is a `git pull`. Committing the output keeps the deploy
  unchanged and makes every published page reviewable in the pull request.
- Keeping JavaScript translation and adding `hreflang` only: search engines
  still see one language per URL; the content plan needs a URL per language.

## Consequences

- Publishing an article is a Markdown file, `python -m sitegen build` and a
  commit; reviewers see the sources and the rendered HTML in one diff.
- Generated files are marked `linguist-generated` so pull-request diffs collapse
  them; they must never be edited by hand.
- Sources (`content/`, `templates/`, `sitegen/`) are served by nginx together
  with the output; `robots.txt` disallows them on bible.garden.
- nginx still answers unknown URLs with `index.html` and status 200; serving the
  generated `404.html` with status 404 needs an `error_page` rule on production,
  tracked separately.
